# CS 305 Artemis Financial

This repository contains my [Practices for Secure Software Report](artifacts/CS305_ProjectTwo_Practices_for_Secure_Software_Esteban_Garcia.docx) from CS 305 Project Two. It documents the changes I made to the Artemis Financial sample application and the testing I used to check them. This was a local course project, not a production deployment.

## Reflection

Artemis Financial is a financial-planning company that wanted its web application to transfer information securely and verify that data had not changed. The starter application did not have the required checksum endpoint, and its HTTPS settings were unfinished. I think I did well at checking both the code and the dependency report instead of assuming that a successful build meant the application was secure. Secure coding matters for this client because a mistake could expose or alter customer financial information. It also helps the company maintain customer trust and avoid the cost of fixing preventable security problems later.

The most challenging part of the vulnerability assessment was interpreting the dependency scan. The older framework already had reported vulnerabilities, so I needed to separate those existing findings from anything my changes might introduce. The vulnerability assessment process flow helped me focus my manual review on the areas this small application actually used, especially cryptography, client/server communication, the API controller, and code quality. I added a SHA-256 checksum check, configured HTTPS with a certificate for local testing, and wrote tests for both the expected data and altered data. In a future project, I would use the same combination of code review and dependency scanning, then look at each finding's affected version and how the application uses that component before choosing an upgrade or another mitigation.

I checked functionality by running three Maven tests and opening the `/hash` endpoint in a browser, where the checksum verification returned PASS. I also tested the HTTPS connection using the exported certificate rather than turning off certificate validation. After the refactor, I ran OWASP Dependency-Check again and compared its results with the baseline; the second scan did not show any new vulnerable dependency findings. That does not mean the application is ready for production. The certificate is self-signed, and the starter project's older dependencies still need attention.

Java Keytool, `MessageDigest`, Maven tests, OWASP Dependency-Check, and the assessment flow diagram were the most useful resources and practices in this project. I would use the report as an example for a future employer because it shows how I reviewed an existing application, made a focused security change, tested the behavior, and documented what still needed work. Being clear about those remaining limitations is part of doing a responsible security review.
